01 · Interface

Contract: label maps only, never blended previews

This is the single coupling point of the whole pipeline, so the tool defends it actively.

Why a blended preview must be rejected Its colours are contaminated by the greyscale, so it is not a label map. Processed anyway, every class boundary would be wrong — and wrong in a plausible way: nothing crashes, it just quietly returns a page of bad numbers.

What the tool does: snap RGB onto the standard palette, count off-palette pixels, and error out above 5%.

P / L mode  → index IS the class id, read directly
RGB mode    → snap to palette, error if >5% off-palette
other modes → unsupported
Why the palette is invertible build_palette() is the PASCAL VOC colormap with the leading black entry dropped, so class id == palette index. The annotation tool and the metrology tool call the same function, so the two can never drift apart.

② One job = three YAMLs, deep-merged

The web app never asks anyone to write a full config; it is split into three files, merged at launch.

Dataset config  ─┐
Training config ─┼─►  deep-merged YAML  ─►  training entry script  ─►  stdout parsed into TrainingLog

Precedence: dataset → training → model  (later wins, merged per key)
ConfigOwnsTypical content

Why a deep merge, not concatenated text Concatenation produces duplicate top-level keys. Parsers tolerate it (last wins), but the document is invalid YAML and re-reading it throws Map keys must be unique.

02 · Segmentation training

③ Three hard constraints of segmentation training

All learned the hard way. Each one either kills the run or makes a setting silently ineffective.

1 · It trains by iteration, not epoch iters is the total step count; likewise warmup_iters and save_interval. The epoch-named database columns hold iteration counts for segmentation projects.
2 · len(loss.types) must equal the number of logits the model emits Main head + auxiliary heads. A mismatch gives RuntimeError: The length of logits_list should equal to the types of loss config.
So loss: always lives in the model config, never in the training config — that way any training preset combines with any model preset without a mismatched loss.

03 · Metrology tool

Two premises behind every number: scale & rectification

Scale (nm/px)　Read from the filename by regex: ..._FOV_76.37nm.png → 76.37 nm, divided by the actual image width. All 26 images parsed: 76.37 / 1024 = 0.074580 nm/px.

  • Dividing by the real width rather than a hard-coded 1024 keeps it right if a mask is exported at another size; a width ≠ 1024 warns
  • fov_nm / image_width_px / scale_nm_per_px / scale_source all go into the JSON and CSV
  • No FOV and no --scale-nm is a hard error — never a silently wrong scale

Rectification　The Leveling layer is fitted to a line for the tilt angle, and the image is rotated flat before measuring. "dy is how far down it sits" only means anything after this step.

  • Interpolation must be nearest-neighbour: the array holds class ids, and averaging invents classes never predicted
  • Padding is 255 (ignore), not 0 (background) — "outside the frame" stays distinguishable, which is what M5's crop rejection relies on
  • Every point carries both rectified and original coordinates, so results overlay back on the raw TEM image
  • Cost: 1–2 px resampling noise. Self-test residual angle 0.007°, but dy error can reach ~5 px; --no-rotate avoids it entirely

04 · Measurement M1

leveling — the rectification datum

The only module whose result feeds back into every other measurement.

DefinitionLeveling class → largest component → Guo–Hall skeleton → line fit → tilt angle
AngleTLS (total least squares). OLS systematically flattens the slope when residuals are comparable to the x-span; TLS is orientation-unbiased
R²/rmseOLS y~x, because that is what "fit R²" normally means. Both are reported so the difference is visible
Reliabilityangle_stderr_deg (slope standard error), not R²
Self-checkRe-fit after rectification; residual angle > 0.05° warns
Measured26 images: median tilt 0.259°, range −2.263°…+1.002° (mounting tilt within ±2°)
R² is meaningless for near-horizontal layers R² = 1 − SS_res/SS_tot, and for a horizontal layer SS_tot (the variance of y) is itself tiny — an excellent line 1029 px long with only 1.9 px rmse still scores R² ≈ 0.02.
Leveling / MgO_C / Non_mag are all like this. Results carry fit_r2_degenerate: true and an explanatory fit_r2_note.
Judge straightness by rmse and max_residual.
The post-rectification re-fit is a free self-check If the rotation matrix, the inverse transform or the coordinate mapping were wrong anywhere, the residual angle would not come out near zero. This check runs on every image at negligible cost.
04 · Measurement M2

mgo_c — MgO_C straightness and tilt

DefinitionMgO_C skeleton → TLS line
b3 / b4The extreme (min/max x) skeleton points projected onto the fitted line
Outputangle, fit_r2 (+degenerate flag), fit_slope/intercept, rmse, max_residual, perp_rmse, b3/b4, fit_length, residual_profile
Measuredrmse ≈ 0.045 nm (0.6 px), max_residual ≈ 0.126 nm; tilt −3.5°…+3.5° across the batch
Why b3/b4 exist rather than only b1/b2 b1/b2 are the raw skeleton tips; b3/b4 are the endpoints of the straight-line model. The difference between them is the local waviness.
So both a1→b1 and a1→b3 are reported: the first targets the real tip, the second the model and is insensitive to local burrs.
Measured: dx agrees to 0.001 nm (medians 5.332 / 5.333 nm), but b3 has smaller dy scatter.
04 · Measurement M3

interfaces — interface endpoint offsets (the core metric)

Endpointsa1 = SAF_Ru_L skeleton tip at max x · a2 = SAF_Ru_R tip at min x
b1/b2 = MgO_C skeleton tips at min/max x · b3/b4 = MgO_C fitted-segment endpoints
Four offsetsa1_b1 · a1_b3 · a2_b2 · a2_b4, each with dx/dy/distance (px + nm)
Sign conventiondx>0 = b is right of a; dy>0 = b sits lower than a. Written verbatim into every offset's convention field
Measureda1_b1.dx median +5.332 nm (σ 0.61), a2_b2.dx −5.332 nm (σ 0.50) — strictly symmetric
Skeleton tips retract Guo–Hall (like any morphological thinning) pulls back from the region tip by roughly half the band width. On a synthetic 13 px thick layer the retraction is exactly 6 px.
--endpoint-extend region extrapolates along the tangent to compensate (self-test a1 error is 0 in that mode); off by default to stay faithful to Guo–Hall.
The saving grace: dx/dy are differences of two endpoints, so similar retractions largely cancel.
04 · Measurement M4

*_dip — max downward excursion within 5 nm of the tip

Walking 5 nm back along the skeleton from a1 (or a2), how far down does the layer dip? It characterises tip sagging.

BaselineThe endpoint itself: dev = y − y(endpoint), positive = lower
WindowMeasured along arclength, not along x
Outputwindow · window_polyline · max_downward_deviation · max_downward_point · max_downward_arclength · max_abs_deviation · deviation_profile
MeasuredLeft 0.597 nm (0…1.417), right 0.709 nm (0.224…1.268)
Why arclength and not x The layer bends near the tip. An x-window would cover a different amount of actual layer on different images, making the numbers incomparable.
Why the whole deviation_profile is stored To try a different window length, or to check whether the maximum is an isolated burr, you do not re-run the batch — you check the JSON.
M5's curvature_profile and M2's residual_profile follow the same rule; it is a principle running through the whole tool.
How it is drawn (magenta) Thickened skeleton span = the searched range · end ticks = window bounds · dashed line = the endpoint baseline · arrow to the maximum with its value. The number is readable without opening the JSON.
04 · Measurement M5 (1/2)

milling_l/r — which flank?

A Milling band has two flanks: one against the stack, one facing vacuum. We want the one the ion mill actually produced.

Adopted: adjacency criterion Default outer keeps boundary pixels touching no other class, then takes the longest contiguous run in contour order. Completely independent of the skeleton normal.
Rejected: splitting by the skeleton normal The original proposal was to split the boundary with the skeleton and keep the positive-normal side. Measured per point: 
i= 411 p=(420,682) +n→_background_  -n→MgO_L
i= 651 p=(431,443) +n→Block_U       -n→_background_
The stack is on the negative side low down and the positive side higher up — no single sign holds one flank along the whole band; the selection flips partway.
The image crop fabricates the sharpest corner The bands run off the field of view, so the outer edge includes a straight cut and two 90° corners — the highest curvature anywhere. Before this rule, m2 landed on the right image border.
Boundary pixels within 4 px of the frame or the rotation padding are now discarded. (Padding with 255 = ignore exists exactly for this: after rectification the cut becomes an interior slanted line, and the only remaining evidence that it is a crop is that its far side lies outside the original frame.)
04 · Measurement M5 (2/2)

milling_l/r — locate with the spline, quantify with the circle

The edge is smoothed with a cubic B-spline and the curvature taken analytically. Straight tails sit at κ≈0 and cannot win, so no piecewise straight–curved–straight model is needed.

Curvature magnitude is scale-dependent, and the spline underestimates it A smoothing spline reduces the knot count until the residual matches s, and a handful of cubic segments cannot hold constant curvature. On a synthetic arc of true radius 200 px: the spline reports 168 px (−16%), the osculating circle 190 px (−5%).
FieldUse forNotes
radius / kappa_*Locating m1/m2Spline derivatives: position reliable, magnitude ~15% low
local_circle.radiusMagnitudeCircle fitted to the raw edge points at that spot, accurate to ~5%
local_circle.rmsConfidenceA real bend is not an arc; 1–2 px is normal. Above 3.5 px, reliable=false plus a warning
tail_left/rightModel checkLine fits over the outer 25% of arclength; also usable as the milled sidewall angle
"The middle curve" has no objective definition The bend sits at about 73% of the arclength, not the midpoint, so --milling-middle-frac defaults to 1.0 (unrestricted) — straight sections cannot win the maximum anyway. A maximum landing on a band boundary raises a warning.
This explanation ships inside the JSON The magnitude_note field tells whoever reads the data which radius to use, without depending on anyone having read the docs.
Measured over 26 images: m1 circle radius median 4.835 nm, m2 5.329 nm.
04 · Measurement M6

non_mag — horizontal edge and endpoints

Which edgeDefault auto: count how many columns of each edge touch Block_D and take the one with fewer. Sample image top:172 / bottom:0 → bottom edge. Not hard-coded as "bottom", so a flipped sample or a relabelled stack cannot silently measure the wrong interface
Edge extraction　The extreme foreground pixel per column. Both Non_mag edges are single-valued in x, so this is the edge — no side-selection heuristic to get wrong
Fit　Sigma-clipped (2σ) TLS. The two corners round off and would otherwise drag the line
Endpoints　The fitted line is extended out to the min/max x column of the region, not stopped at the fitted columns
Why the endpoints extend to the region boundary The clipped columns are exactly the rounded corners. Stopping there makes the endpoints move with the clipping threshold; extending to the region boundary makes them a property of the region instead. y is taken from the line, not from raw pixels, so the rounding never contaminates it.
"Largest component" is not the same as "the right one" In one of the 26 images the prediction grew a Non_mag band across the bottom of the frame whose area (11128 px) was larger than the real box, so the size rule measured the artefact — edge length 33.98 nm against a normal ~10 nm. Non_mag is now anchored on Block_D: candidates are restricted to components touching Block_D, falling back to size only if none do. That image now reads 9.14 nm.
04 · Measurement M7

corner_offsets — Non_mag endpoints ↔ Milling bends

dx/dy and straight-line distance for Non_mag1→m1 and Non_mag2→m2.

What is specialThe only module that combines other measurements. It does not recompute; it reads M5 and M6 back out of ctx.results
OrderingSo it must sit after non_mag / milling_* in the registry
DegradationIf one side's dependency failed, that side alone becomes null and the other is still reported; only both missing fails the module
OverlayA spring-green dotted L — horizontal leg is dx, vertical leg is dy
MeasuredNm1→m1.dx median −1.251 nm, Nm2→m2.dx +1.288 nm (opposite signs, symmetric)
This module demonstrates the architecture's composability Adding a "combining" measurement requires re-implementing no geometry at all — just place it after its dependencies in the registry and read the points back with ctx.measured_point(). Degradation is per side, so a mask that lost one Milling band still yields the other offset.
a = ctx.measured_point("non_mag", "Non_mag1")
b = ctx.measured_point("milling_l",
                       "max_curvature_point")

    ctx.warn(...); return {...: None}

Recommended batch triage

  2. Look at rows where local_circle.reliable == false
  3. Box-plot the core columns to find outliers

06 · Reliability

What selftest.py covers

All synthetic geometry with known ground truth, no real data — so it runs any time, runs fast, and its conclusions are not arguable.

  • Guo–Hall: both implementations are pixel-identical on straight bands, bent bands, random blobs
  • Rotation: round-trip error < 1e-9 px; rotating by the fitted angle lands exactly horizontal
  • Lines: TLS angle error < 1e-6° on an exact line; the R²-degenerate flag fires as expected
  • Circles: analytic curvature radius within 1% (50 / 200 / 600 px)
  • Contours: exact perimeter on a rectangular ring; correct wrap-around run selection
  • End-to-end (untilted): a1/a2/b1/b2, dx/dy, angles, rmse are exact
  • Non_mag auto side: the synthetic mask is isomorphic to the real one; the bottom edge must win
  • corner_offsets: reported dx/dy must equal the difference of the two named points exactly (1e-9 px)
  • Decoy component: a fake band 6× larger than the true Non_mag (57000 vs 9150 px) far from Block_D — the measurement must still land on the real box (reproduces the bad prediction from the real batch)
  • Scale: end-to-end on one image, nm/px must equal FOV/width exactly
  • Milling side selection: inner/outer radii known (200/215 px); each mode must land on the right one
  • Tilt 3° then rectify: recovered tilt error < 0.05°, circle radius error < 10%
The self-test proves "the implementation matches the definition", not "the definition matches the requirement" Those are two different things. The second needs a set of manually measured images as a reference — see the second-to-last slide.
07 · Extending

Adding a measurement: one file plus one registry line

The architecture exists to make this cheap. No existing module has to change.

def measure(ctx: AnalysisContext) -> Dict[str, Any]:
    # 1. Mask: prefer_near picks the component by adjacency, not area
    mask = ctx.mask(CLASS, prefer_near=AWAY_FROM)

    # 2. Geometry: skeletons are cached
    line = ctx.centerline(CLASS, extend=("xmin","xmax"))
    tls  = fit_line_tls(line.pts)   # angle from TLS
    ols  = fit_line_ols(line.pts)   # R2 / rmse from OLS
    p1, p2 = tls.endpoints_spanning(line.pts)

    # 3. When unsure, warn. Never fail silently
    if ols["axis"] != "y~x":
        ctx.warn("...")

    # 4. Distances via ctx.dist, points via ctx.point,
    #    offsets via ctx.offset
    return {
        "skeleton_length": ctx.dist(line.length),
        "angle_deg_image": tls.angle_deg_image,
        "rmse": ctx.dist(ols["rmse_px"]),
        "blockD1": ctx.point(p1),
        "blockD2": ctx.point(p2),
        "endpoint_rule": "...",   # rule goes into the data
    }

08 · Limits

Known methodological limits

These are not bugs; they are the boundaries of the method. They are stated so nobody misuses a number.

1 · Skeleton tips retract Inward by about half a band width by default, largely cancelled by taking differences. Use --endpoint-extend region when absolute endpoints matter.
2 · Rectification adds 1–2 px of resampling noise The self-test residual angle is 0.007°, but dy error can reach ~5 px. For dy-sensitive metrics, consider --no-rotate and handling the tilt analytically.
3 · Curvature is a scale-dependent quantity There is no unique "true" curvature on a 1 px quantised edge. Two numbers are given (spline and osculating circle) with their biases documented, but the user must know which one they are using.
4 · Segmentation error is not quantified — the largest unquantified error source in the pipeline The metrology tool assumes the label map is correct. If segmentation places a boundary 2 px off, every downstream number shifts by 0.15 nm, with no warning at all.
The only mitigation today is --overlay-on: draw on the raw TEM greyscale and catch it by eye.
